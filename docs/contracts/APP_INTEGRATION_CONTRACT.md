# App capture (as inspected) and the local app <-> MRCD integration contract v1

Part A documents what the web app **actually does today** (read-only inspection of `ORATORIA-PROYECTO` @ `f46a2b8638b221e44d3cf492cf517f33b68dd0cb`, branch `refactor/f0-guardrails`; nothing was run or modified there). Part B is a **PROPOSED** contract: nothing in the app calls MRCD today, and the app hosts ORATORIA-ENGINE v0 (3 classes), not MRCD (7 classes). Part B adopts, and does not redefine, the MRCD-side contract `mrcd.analysis/v1` that already exists in this repo (`mrcd/service/contract.py`, `mrcd/service/schemas/mrcd.analysis.v1.schema.json`, commit `955d27c`, written by another task). Where this document needs something that contract cannot carry (session link, gaps, report view) it adds **app-side** records in `schemas/app_integration.v1.schema.json`.

Paths below are relative to the app repo unless prefixed `mrcd/`.

Gaps between the app and what MRCD needs (all real):

1. MRCD needs a **continuous mono 16 kHz WAV of at least 13 s**; the app streams 160 ms chunks and keeps no audio. Any integration needs a **new temporary buffering of PCM** on the backend (an owner decision, see B.8).
2. Chunks can be missing (sequence gaps). MRCD has no representation for a gap inside the submitted audio (the live path records `audio_lost` gaps; the service v1 does not).
3. Browser DSP (echo cancellation/noise suppression/AGC) and linear-interpolation resampling alter F0/RMS features the checkpoint was not trained on; the effect was not measured.
4. No audio/video offset or identity verification exists, so no fusion of video with audio is justified.

## Part B. Contract v1 (PROPOSED)

### B.1 Roles and transport

|                        |                                                                                                                                                                                                |
| ---------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Producer of audio      | app backend (it already receives the PCM chunks). The browser never talks to MRCD directly                                                                                                     |
| Consumer               | MRCD service `mrcd.service` (dev server `python -m mrcd.service serve`, loopback `127.0.0.1:8765`, no authentication, no TLS, CORS only if `--cors-origin` is given)                            |
| Request                | `POST /v1/jobs?asr_profile=p0&head=&include_text=false` with the **raw WAV bytes** as body (PCM16, mono, 16 000 Hz). 202 with a job document `mrcd.job/v1`                                     |
| Poll                   | `GET /v1/jobs/{job_id}` until `status` in `completed` / `failed`. `GET /v1/health`, `GET /v1/schema`                                                                                           |
| Offline alternative    | `python -m mrcd.service analyze <wav> --out result.json [--asr-profile p0] [--head vc] [--include-text]` (file in, JSON out; same document)                                                    |
| Response schema        | `mrcd.analysis/v1` (authoritative: `mrcd/service/contract.py`). Real example: `examples/service_analysis_v1.json` (success) and `examples/service_error_audio_too_short.json` (failure)        |
| Limits (from the code) | body <= 64 MiB (`payload_too_large`, 413); queue 8 jobs (`queue_full`, 429, retryable); 32 finished jobs kept in memory; audio duration limit configurable (`--max-duration-s`, default 600 s) |

Exact command that produced the real examples (after generating the excerpt, see `examples/provenance.json`): `HF_HUB_OFFLINE=1 OMP_NUM_THREADS=4 .venv/Scripts/python.exe -m mrcd.service analyze <excerpt.wav> --out docs/contracts/examples/service_analysis_v1.json`; the failure example used a 5 s excerpt of the same audio.

### B.2 Request rules (what the app must guarantee)

1. Audio: PCM16 WAV, **mono, 16 000 Hz, 13 s or longer**. The service never downmixes or resamples (error codes `audio_not_mono`, `unsupported_sample_rate`, `unsupported_audio_format`, `invalid_audio_file`, `audio_not_finite`, `audio_too_short`, `audio_too_long`).
2. **Contiguity.** Only audio that is contiguous in capture time may be submitted. If chunks are missing (`secuencia` gap), the app must either (a) submit the longest contiguous run(s) separately, each with its own binding, or (b) not submit and report `not_run` with the reason `audio gap`. It must **not** silently zero-fill and present the result as complete. Gaps are recorded in the binding (`gaps[]`). Zero-filling is a conscious option only if the binding says so.
3. **No resampling in the integration.** The app already produces 16 kHz; if a different rate ever appears the request must fail with a visible reason.
4. Options: `asr_profile` = `p0` (default). `p1_disfluent_prompt` is experimental and must never be the app default; the service also accepts the experimental opt-in profiles `p0_noloop`, `p1_noloop`, `p0_cuda`, `p1_cuda` (marked experimental with specific warnings; GPU profiles return `asr_unavailable` instead of falling back to CPU; see `ASR_PROFILES_CONTRACT.md` section 1b), none of which may be the app default; `head=vc` is experimental and turn-level and must be requested explicitly. `include_text=false` by default (privacy); transcript text is only requested when the product needs it.
5. No personal data in the request: no names, no `codigo_anonimo`, no session id. The only link is app-side (B.5).
6. Video is not part of the request. There is no endpoint that accepts video or frames.

### B.3 Response rules (what MRCD guarantees, from the existing schema)

- `schema_version` = `mrcd.analysis/v1`; `status` = `completed` | `failed`; on failure `error = {code, message, retryable, details}` and `events = []`, `summary = null`.
- **A measure that is not available is `{available:false, value:null, unavailable_reason:<text>}` and never `0`** (`request.audio_duration_s`, `sample_rate_hz`, `channels`, `summary.events_per_minute`). Modalities are `{available, reason}`; `kinesic_video` is always `available:false` with the reason "service v1 receives audio only".
- Every event: `id`, `class`, `start_s`/`end_s` (seconds from the first sample of the submitted audio), `interval_semantics = "decision_stride_not_human_boundary"`, `score = {value, kind, calibrated:false, label:"uncalibrated"}`, `n_windows`, `modalities_used`, `text` (null unless requested), `validation`, `experimental`.
- Provenance: `provenance.{service, checkpoint (file, sha256, labels), asr (profile, prompt hash, model hash, decode params, profile_fingerprint, anomalies), head, config, environment}` and `request.audio_sha256` (hash of the submitted bytes).
- `warnings[]` always carry `scores_uncalibrated` and `no_human_validation` plus `engine_provenance` (the checkpoint's "PRUEBA DE HUMO" text) and, when applicable, `environment_not_pinned`; `experimental.{active, components}` flags p1/Vc.
- Not present by design: an `uncertain` state, calibrated probabilities, uncertainty values, any visual evidence, any inference about emotion, anxiety, doubt or intention.

RESOLVED 2026-10-31 (contract revision 1.1, additive): `score.kind` is now `max_window_softmax_score` (a raw, uncalibrated softmax maximum, not a probability). The old value `max_window_class_probability` is a DEPRECATED ALIAS: the schema still accepts it so revision-1.0 documents and fixtures validate, but the service never emits it. `provenance.service.contract_revision` = `"1.1"` identifies the new behaviour. Consumers should accept both values and ignore the word "probability" in the old one. Removal of the alias is deferred to a future major contract (v2).

### B.4 Time mapping

MRCD times are seconds from the first sample of the submitted audio. The app maps them to session time with the binding: `start_session_ms = t0_ms_first_chunk - session_t0_ms + round(start_s * 1000)` (or, if the report uses epoch ms, `t0_ms_first_chunk + round(start_s*1000)`). `build_report_section.py` shows the mapping with `audio_start_session_ms`. The interval keeps the semantics "decision stride, not a human boundary": the UI must not show it as the duration of the phenomenon.

### B.5 Session <-> inference link (app side)

The app stores a **binding** (`oratoria.mrcd-binding/v1`, schema `$defs.binding`, illustrative example `examples/app_session_binding_example.json`, placeholder ids): `session_id` (from `session_started`), `segment_index`, first/last `secuencia`, `t0_ms_first_chunk`, `n_chunks`, `duration_ms`, `sha256` of the submitted WAV, the MRCD `job_id`, `asr_profile`, `head`, `include_text`, `gaps[]`, and the capture conditions (`echo_cancellation`, `noise_suppression`, `auto_gain_control`, `resampler`). Integrity check: `binding.audio.sha256 == analysis.request.audio_sha256`; a mismatch invalidates the result. The binding is the only place where a session id and a MRCD result meet.

### B.3b Contract revision 1.2 (additive, 2026-11-01, S3)

`provenance.service.contract_revision = "1.2"`. Everything below is optional or backward compatible: a revision 1.1 document still validates.

- **Output scope.** Default `request.output_scope = "evaluated"`: only `filler_word`, `prolongation`, `repetition` are emitted. `block`, `rhetorical_pause`, `neutral_pause` and `revision` appear only with the explicit option (`--include-out-of-scope`, `include_out_of_scope=true`, `output_scope="all"`); each such event has `in_scope: false`, `validation: "out_of_scope_unvalidated"`, `experimental: true`. They are never counted: `summary.n_events`, `summary.counts_by_class` and `summary.events_per_minute` cover in-scope events only; `summary.out_of_scope = {included, n_events, counts_by_class}` reports how many were detected (hidden or included). A `out_of_scope_hidden` / `out_of_scope_included` warning says which.
- **Prolongation** events carry `validation: "observable lengthening; disfluent function not demonstrated"`.
- **Optional three-state `decision`** (`decision=true`): `event.decision = {state: present|absent|uncertain, estimate, lo, hi, basis, calibration_claim: "none"}`. `estimate` is a development-fitted Platt mapping of the score; the abstention band `[lo, hi)` was chosen on DIHANA folds 1-4 (S3 E3). It is EXPERIMENTAL and never a demonstrated calibrated probability; `score.calibrated` stays `false`.
- **Optional experimental text route** (`text_route="rep_ctx_p1"`): replaces the V0 `repetition` events with segments scored by a turn-level logistic model on P1 ASR text (`score.kind = "text_route_logistic_score"`, `modalities_used = ["linguistic"]`, `provenance.text_route`). Needs the engine's opt-in `analyze(return_words=True)`. **Unit (declared 2026-11-01, review S):** the model was trained and evaluated on whole DIHANA turns; the route applies it to ASR segments split at pauses >= 0.6 s or 30 words. That segment-level behaviour was **not evaluated**.
- `scores_uncalibrated` now says "maximum window softmax score ... (softmax, not calibrated)". UI copy should read "score (softmax, no calibrado)", not "probabilidad de clase".

### B.3c Contract revision 1.4 (additive, 2026-11-02, O integration)

`provenance.service.contract_revision = "1.4"`. Documents of revisions 1.0-1.3 (without the fields below) still validate.

- **Decision profile.** `request.decision_profile` (`"o2026_11"` | `"v0"`) and `provenance.decision_profile` = `{name, status, classes, calibration_claim: "none", pipelines_verified, note}`. `classes[<c>].route` says where each class comes from: `o_campaign_unit_pipeline` (with `artifact`, `artifact_sha256`, `source_pickle_sha256`, `pipeline_version`, `unit`, `asr_profile_trained_on`) or `engine_v0_window_events`.
- **`o2026_11` (service default; `status: "exploratory"`).** **The F1 figures below (filler 0.697 vs V0 0.567, prolongation 0.619 vs 0.458) were measured on DIHANA TURNS and do NOT apply to this service, which applies the pipelines to pause-delimited segments (unmeasured domain shift); do not quote them in product material.** `filler_word` and `prolongation` events come from the O-campaign per-class pipelines (DIHANA folds 1-4, nested CV by speaker, exploratory) applied to ASR segments split at pauses >= 0.6 s (max 30 words). Their events have `score.kind = "unit_pipeline_model_score"`, `modalities_used = ["acoustic","linguistic"]`, `n_windows` = windows of the segment clip, `validation` = the exploratory-unit text, and an interval equal to the **segment span** (coarser than the V0 3 s windows; still "decision stride, not a human boundary"). `repetition` and every other class keep the engine decision (or the opt-in `text_route`). A warning `decision_profile_exploratory` is always present; `decision_profile_asr_mismatch` when the ASR profile is not `p0` (the pipelines then read the words of the requested profile; safe choice: warn, do not reject nor re-decode); `decision_profile_no_words` when the ASR returned no words (filler/prolongation "not available", never 0).
- **`v0` (explicit opt-in: `decision_profile=v0`, `--decision-profile v0`).** The historical engine events of every class; the document equals the revision 1.3 one except for the additive fields.
- **`decision=true` with `o2026_11`.** For pipelined events `event.decision` is the pipeline's own three-state (`basis: "o_campaign_unit_pipeline_inner_band_uncalibrated"`; band chosen in the inner CV; `estimate` is the raw score because the campaign chose no calibrator, `calibration_claim: "none"`).
- **Integrity.** The service reads only plain-JSON artifacts (`mrcd/service/profiles/o2026_11/*.json`), compares their sha256 with the values pinned in `mrcd/service/decision_profile.py` before parsing, and refuses an altered file: `analysis_failed` with a message pointing to `decision_profile=v0`; at start-up (`preload`) it raises. No pickle is read by the product.
- **Library vs product.** `DisfluencyEngine.analyze` always returns V0 events (reproducible history, experiments). Only the service (and therefore the app) selects a profile; the default is `o2026_11`.
- Fixtures: `examples/service_analysis_v1_4_default_profile.json` (o2026_11, `decision=true`, `include_text`), `examples/service_analysis_v1_4_v0.json`.

### B.6 What the report may show (`oratoria.mrcd-report/v1`)

Schema `$defs.report_section`; reference mapping `build_report_section.py`; real examples `examples/app_report_section_example.json` (from the real success document) and `examples/app_report_section_failed_example.json`. Rules:

1. Show the class, the session-time interval and the score **with the label "no calibrado"** (`score.label = "uncalibrated"`); never as a percentage of certainty or a probability.
2. Show `warnings` (at least `scores_uncalibrated` and `no_human_validation`) and the `experimental` flag.
3. For classes without a compatible human reference (`block`, `rhetorical_pause`, `neutral_pause`, `revision`): since revision 1.2 the service hides them by default; when they are requested, show them only with the qualifier `out_of_scope_unvalidated`, outside totals and rates; never as a validated finding (see `DISAMBIGUATION_SPEC.md`).
4. A missing measure is rendered as "no disponible" **with the reason**, never as `0`. A failed or not-run analysis renders its `unavailable_reason`.
5. Rates per minute are not meaningful for short or padded audio; the service returns `events_per_minute` as a measure, and the UI must show its availability and audio duration next to it, never an unqualified number.
6. Do not aggregate `todas_las_probabilidades` or window rows into counts, and do not subtract from composite criteria of the literature (project rule 5).

### B.6b Video and the visual channel

MRCD receives **no video**; `kinesic_video` is reported unavailable with a reason. The app's `vision_summary` indicators (face detected, head toward camera, hand gesture, stable posture, as proportions) are **observable signals**; they may be shown next to MRCD output **without fusion** and without interpretation. Forbidden everywhere: mapping them to anxiety, doubt, intention, emotion or any diagnosis. Fusion of audio and video requires, first, a measured audio/video offset and speaker identity verification (neither exists), and its usefulness is a hypothesis (H2) with no measured result.

### B.8 Privacy, retention and security (open decisions for the owners)

- **New retention.** To build the WAV the backend must buffer PCM. Proposed minimum: in memory (or an OS temp file removed in `finally`), per segment, deleted as soon as the job finishes; never written to the database; the binding keeps only the hash. This changes the current "no raw audio retained" property and needs an explicit owner decision and consent text. The MRCD dev server itself decodes in memory, writes nothing to disk and keeps only JSON results (bounded, in memory).
- Transcript text is off by default (`include_text=false`).
- The dev server has no authentication or TLS: loopback only; refuses non-loopback binds unless `--allow-non-loopback`. Do not expose it. No keys or personal data are exchanged.
- Logs must not contain audio or transcript content.

### B.9 Versioning and compatibility

- The response is versioned by `schema_version` (`mrcd.analysis/v1`, `mrcd.job/v1`). The app must reject an unknown major version (`contract_version_unsupported`) and ignore unknown additive fields only if the contract is later declared additive; the v1 schema is currently **closed** (`additionalProperties:false`), so any new key requires a new version.
- App-side records are versioned independently (`oratoria.mrcd-binding/v1`, `oratoria.mrcd-report/v1`).
- This document does not change the taxonomy (7 classes + `fluent`), does not add classes, and does not add certainty the engine does not support.

### B.10 Acceptance checks for the integration (for the implementer; none has been run)

1. A 20 s contiguous excerpt yields a `completed` document whose `request.audio_sha256` equals the binding hash.
2. A 5 s excerpt yields `failed/audio_too_short` and the report shows "no disponible" with the reason, not an empty or zero value.
3. A missing-chunk gap yields `not_run` or separate runs, never a silently padded result.
4. The report shows "no calibrado" next to every score and never renders `events_per_minute` without availability and duration.
5. `kinesic_video` is rendered as unavailable; no vision indicator is mapped to an internal state.
6. Disconnecting MRCD leaves the session and the rest of the report intact.
7. `docs/contracts/validate_examples.py` passes against the produced documents.

### B.11 What was verified here and what was not

Verified: the app facts in Part A by reading the sources listed; the service contract by validating real outputs with the in-repo validator (`validate_examples.py`); the report mapping on real service output. **Not verified:** any real browser capture, any real WebSocket session, retention beyond grep-level evidence, the audio/video offset, the effect of browser DSP on MRCD features, an end-to-end app -> MRCD run (it does not exist), the microphone.

### B.12 Flow as implemented in the app (2026-11-01, branch `feat/mrcd-integration`; supersedes the "proposed" flow where they differ)

Self-review by the authors; no independent review. Privacy option B was decided by the team on 2026-11-01 (advisor ratification pending; see `PRIVACY_DECISION.md`, section 6).

1. **Capture.** `/ws/session` is unchanged on the wire. The backend keeps the PCM16 chunks of the session in a per-session in-memory buffer (`platform/mrcd/audio_buffer.py`), capped by `ORATORIA_MRCD_MAX_AUDIO_SECONDS` (default 600 s, equal to the service default). When the cap is passed the buffer stops growing, the client receives one `error` message with `codigo = limite_audio_analisis_excedido`, the session keeps running and the report says `unavailable / audio_limit_exceeded` (nothing partial is sent). A `secuencia` gap is recorded and the session is reported as `unavailable / audio_gap` (the contract's option (b); no zero-fill, no splitting into runs yet).
2. **Hand-off.** On `close_session`, and also on abrupt disconnection, the buffer is handed to `MrcdSessionAnalysis`. It stores a `pending` document, then a background task builds the WAV in memory, calls `POST /v1/jobs?asr_profile=<p>&include_text=false` and polls `GET /v1/jobs/{id}` (service URL from `ORATORIA_MRCD_SERVICE_URL`; empty = feature off and no audio is buffered). The buffer is erased in a `finally` on success, MRCD failure, unexpected error, cancellation (shutdown) and store failure. A failure never fails the session.
3. **Stored document** (`practice_session.mrcd_analysis`, JSONB; exposed unchanged as `mrcd_analysis` in `GET /api/v1/sessions/{id}`): `schema = oratoria.mrcd-session-analysis/v1`, `status = pending | completed | unavailable`, `calibrated = false`, `output_scope = evaluated`, `classes_in_scope`, `asr_profile`, `provenance`, `binding` (`session_id`, `n_chunks`, first/last `secuencia`, `t0_ms_first_chunk`, `buffered_duration_s` or `null`, `gaps`, `audio_sha256`), `unavailable = {code, reason} | null`, `analysis = <mrcd.analysis/v1 document> | null`. `binding.audio_sha256` must equal `analysis.request.audio_sha256`; a mismatch becomes `unavailable / binding_hash_mismatch`. Only this JSON is persisted; no audio and no transcript text.
4. **Error mapping to `unavailable`** (B.7 codes kept): service codes pass through (`audio_too_short`, `queue_full`, `asr_unavailable`, ...); app-level codes are `mrcd_unreachable`, `mrcd_timeout`, `mrcd_bad_response`, `contract_version_unsupported`, `audio_gap`, `audio_not_buffered`, `audio_limit_exceeded`, `binding_hash_mismatch`, `analysis_failed`, `analysis_cancelled`.
5. **Report.** The browser never talks to MRCD for the session report: `ReportPage` reads `mrcd_analysis` from the session detail, polls it while `pending`, and renders only the default scope (`filler_word`, `prolongation`, `repetition`) with "Score (softmax, no calibrado)", timestamps, provenance and warnings, "No disponible: <reason>" otherwise, no percentages and no psychological states. The manual WAV upload (direct browser to MRCD) remains only as a development tool behind `VITE_MRCD_DEV_UPLOAD=true` plus `VITE_MRCD_SERVICE_URL`, off by default.
6. **Not done / limits.** No authentication or TLS between app and MRCD; no per-process cap on concurrent buffered sessions (memory use is up to `max_audio_seconds * 32 000` bytes per active session, plus a transient copy while the WAV is built); the immutable `bytes` copy of the WAV cannot be zeroed and is released to the garbage collector; the live mode of the app still runs ORATORIA-ENGINE v0, not MRCD; no consent text mentions the in-memory audio analysis yet.

#### B.12 addendum 2026-11-01 (corrections after the independent review; supersedes items 1, 2, 4 and 6 where they differ)

Self-review by the authors. Details and the exact persisted set are in `PRIVACY_DECISION.md`, section 7.

- **Opt-in.** The buffer is created only for accounts with an active consent for the current consent-text version (`mrcd_consent` table, `GET/PUT /api/v1/users/me/mrcd-consent`). Without it nothing is buffered, MRCD is not called, and the document is `unavailable / no_consent` ("No disponible: sin consentimiento para análisis de audio"). The consent is re-checked at hand-off.
- **Stored document.** `analysis` is the allow-listed copy of the service answer; `events[].text` and `transcript` are always `null`. Size caps: 2 MiB read from the service, 512 KiB stored.
- **Capacity.** Global and per-account buffer limits, a byte limit and a pending-analysis limit; refusals map to `unavailable` codes `capacity_global_sessions`, `capacity_account_sessions`, `capacity_memory`, `capacity_pending_analyses`, and the client gets the `error` codes `analisis_disfluencias_sin_capacidad` or `analisis_disfluencias_sin_memoria` while the session continues. Usage metrics: `GET /api/v1/mrcd/usage` (superusers).
- **Codes.** `analysis_cancelled` is now `analysis_interrupted` (cancellation when the service stops, and orphaned `pending` documents swept at start-up and every minute), plus `result_too_large`, `contract_violation`, `mrcd_redirect_refused`, `mrcd_response_too_large`.
- **Client.** No redirects, `job_id` validated, cancellable worker thread, plain `http://` only to loopback unless `ORATORIA_MRCD_ALLOW_INSECURE_REMOTE_HTTP=true`.
- **Report.** The frontend stops polling a `pending` analysis after 15 minutes. The manual WAV upload is excluded from the production bundle unless `VITE_MRCD_DEV_UPLOAD=true` at build time.

#### B.12 addendum 2026-11-01 (B incremental, contract revision 1.3; implemented, OFF by default)

Self-review by the authors; no independent review. Design and evidence: `DESIGN_B_INCREMENTAL.md`, `results/mejora_objetivos_20261101/S8_incremental/README_S8.md`. Privacy change: `PRIVACY_DECISION.md`, section 8 (advisor ratification pending).

- **Variants.** *B original* = the backend buffers the PCM and sends the WAV once at close (`ORATORIA_MRCD_MODE=offline`, the default, reference and fallback). *B incremental* = the same in-memory audio reaches MRCD in batches of `ORATORIA_MRCD_INCREMENTAL_BATCH_MS` (2000 ms) while the session runs (`ORATORIA_MRCD_MODE=incremental`); `incremental_verify` runs both and stores the offline result with only `binding.verify = {equal, differing_keys}`.
- **Service (rev 1.3, additive; `mrcd.analysis/v1` documents unchanged).** `POST /v1/sessions`, `PUT /v1/sessions/{id}/audio/{seq}` (idempotent by seq, header `X-Offset-Samples`, optional `X-Content-SHA256`), `POST /v1/sessions/{id}/close` (`total_samples`, `wav_sha256`, `last_seq`), `GET /v1/sessions/{id}`, `GET /v1/sessions/{id}/events` (SSE, counts only, `Last-Event-ID`), `DELETE /v1/sessions/{id}`. `POST /v1/sessions` also returns a `subscription_token`; every other session endpoint requires it in `X-Session-Token` (or `Authorization: Bearer`) and answers `404 session_not_found` otherwise (same answer as an unknown id), except `DELETE`, which answers the same idempotent `204` for an unknown id and for a wrong token and acts only with the token. The terminal SSE event (`completed` / `failed`) carries state and counts only (`status`, `result_available`, `session_id`); the document is read with `GET /v1/sessions/{id}`. Enabled only by `serve --incremental --device cpu --preload <profiles> --warmup`. New error codes: `incremental_disabled`, `session_not_found`, `session_limit`, `sequence_conflict`, `offset_mismatch`, `batch_too_large`, `audio_gap`, `close_mismatch`, `session_closed`, `session_expired`, `profile_not_supported_incremental`.
- **Exactness.** The close runs the unchanged offline `analyze_bytes` on the canonical WAV with an ASR wrapper that answers already decoded 8 s fragments from a per-session cache; Whisper, its parameters, the preprocessing and every later stage are untouched.
- **App.** `IncrementalUploader` (per session, next to the unchanged `SessionAudioBuffer`), progress hub and `GET /api/v1/sessions/{id}/mrcd-analysis/events` (status and counts only; state first; authorised by the bearer token) when `ORATORIA_MRCD_PROGRESS_PUSH=true`. The pending document carries `binding.progress_push`, and the report page then subscribes instead of polling.
- **Fallback.** Any incremental failure cancels the MRCD session (`DELETE`) and runs the B original path with the complete buffer; the stored document says `binding.mode = "offline"` with `fallback_from = "incremental"` and the reason code.

#### B.12 addendum 2026-11-01 (review S8 corrections; self-review, no independent re-review)

- **Access.** Per-session `subscription_token` (random, 256 bits, shown once at open, memory only, constant-time comparison). The app client keeps it in memory and drops it when the session is cancelled or its document was read.
- **Event stream.** No document, text or words on any event, the terminal one included. A late subscriber receives the same counts-only terminal event.
- **Memory budget.** `max_total_audio_bytes` (default 128 MiB) across all live sessions (PCM buffers plus the canonical WAV reserved at close). Exceeding it answers `429 session_limit` (retryable); the app degrades to offline.
- **Scheduling bound.** A close (priority 0) never waits behind queued chunks; it waits for the ONE task running when it is enqueued. A queued `POST /v1/jobs` is promoted to the same class after 20 s.
- **Cancel while closing.** The analysis stops before its next real chunk decode (a safe point); the stage in progress (one chunk decode, or the post-ASR stages) is not interruptible and its result is discarded.
- **Verify mode.** If the offline run fails after a good incremental result, the incremental result is stored (`binding.mode = "incremental"`) with `binding.verify = {equal: null, differing_keys: [], offline_status, offline_code}`; equivalence is never claimed in that case.
